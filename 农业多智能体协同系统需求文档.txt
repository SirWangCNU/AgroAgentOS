AgroAgentOS 农业多智能体协同平台
完整需求分析与技术方案（Markdown 版）
版本：V1.0
日期：2026-05-27
用途：项目立项、原型开发、技术选型、答辩展示、后续迭代

---
1. 项目概述
1.1 项目名称
AgroAgentOS，中文可命名为 智农多智能体协同平台。
该怎么做
项目名称要同时体现“农业”和“智能体平台”两个核心特征。起名时不要只强调“聊天机器人”，因为你的项目不是普通问答，而是一个能够调用知识库、天气、工具和内容生成能力的农业智能平台。名字最好简洁、专业、便于展示，也便于后续做网站域名、GitHub 仓库名和答辩 PPT 标题。

---
1.2 项目定位
本项目是一个面向农业领域的 AI 平台，核心能力包括农业知识问答、实时天气显示、知识库检索、多智能体协同、MCP 工具调用和 AI 营销内容生成。
该怎么做
定位一定要清晰。你不是在做一个通用大模型网站，而是在做“农业垂直场景 AI 平台”。这样做的好处是：
1. 需求更聚焦，容易落地；
2. 评审更容易看到行业价值；
3. 后续功能可以围绕农业不断扩展；
4. 系统的每个模块都有明确用途，不会显得空泛。
在设计产品时，所有功能都应该服务于农业场景。比如，天气不是单纯展示天气，而是结合农业判断“是否适合播种、喷药、施肥、灌溉”。广告生成也不是泛化的文案生成，而是服务于农产品销售。

---
1.3 项目背景
农业生产强依赖环境条件、经验知识和市场信息，但这些信息通常分散在不同来源中，且普通农户不容易快速获取。通用大模型虽然能回答问题，但对农业知识、实时天气和具体任务执行支持不足。
该怎么做
你在文档里要把“为什么需要这个项目”说清楚。可以从以下角度写：
- 农业决策依赖天气和作物状态；
- 病虫害和施肥需要专业经验；
- 农业知识分散且不统一；
- 农产品宣传与销售能力不足；
- 通用 AI 无法自动调用专用工具。
这一段的作用是证明你的项目不是“为了用 AI 而用 AI”，而是真正解决现实问题。

---
1.4 项目目标
项目目标分为四部分：
1. 提供农业知识问答；
2. 提供本地实时天气与农业建议；
3. 建设农业知识库并支持检索增强；
4. 提供农产品营销文案和内容生成能力。
该怎么做
目标不要写得太虚，要写成可实现的功能。每个目标都能落到具体页面、接口和 Agent 上：
- 问答目标对应聊天界面和推理 Agent；
- 天气目标对应天气卡片和天气 API；
- 知识库目标对应文档上传、切分、向量化和检索；
- 营销目标对应模板化输入和内容生成输出。
这样后续开发时就能按目标拆任务。

2. 需求分析
2.1 用户画像
2.1.1 农户
农户需要快速获得种植、施肥、灌溉、病虫害和天气相关建议。
该怎么做
你要把系统设计成“少输入、多输出、可直接使用”的形式。农户通常不希望看复杂参数，因此界面要简洁，回答要直观，建议要具体，例如“未来三天有降雨，不建议喷药”。
2.1.2 农场管理者
农场管理者关注地块管理、作业安排和风险控制。
该怎么做
应该为这类用户预留“地块信息”“作业计划”“天气提醒”等能力，虽然第一版不一定全部实现，但系统结构要预留扩展口。
2.1.3 农业技术人员
农业技术人员关注专业知识、技术规范和资料检索。
该怎么做
知识库要支持引用来源、展示检索片段，这样更适合技术人员使用，也让回答更可信。
2.1.4 农产品经营者
这类用户最需要营销文案、宣传标题、短视频脚本和平台化表达。
该怎么做
营销 Agent 要提供模板化能力，输入产品信息后自动生成不同平台适配内容，如抖音、小红书、朋友圈、直播口播等。

---
2.2 使用场景
场景一：农业知识问答
用户提问“现在适合种玉米吗”，系统结合知识库和天气信息给出建议。
该怎么做
这里的关键不是直接让大模型自由发挥，而是让它先判断是否需要天气、知识库和规则判断，再形成答案。也就是说，回答流程应当是“问题理解 → 工具调用 → 检索 → 推理 → 输出”。
场景二：实时天气辅助决策
用户打开网站就能看到本地天气和农业建议。
该怎么做
天气模块要做成独立卡片，实时展示温度、湿度、风速、降雨概率等，并给出农业行动建议。建议不要只显示天气数值，而要让天气服务于决策。
场景三：知识库问答
用户上传农业文档后，系统能基于文档内容回答问题。
该怎么做
上传后先解析文档，再进行切分和向量化，存入向量库。回答时优先检索知识库，再让大模型基于检索结果作答，减少幻觉。
场景四：农产品营销生成
用户输入农产品信息，系统自动生成广告内容。
该怎么做
这部分要预设输入模板，例如“产品名、特点、价格、平台、风格、目标人群”，然后让模型按模板输出，不要让用户每次都自由表达，否则结果容易散乱。

---
2.3 需求边界
系统第一版要聚焦在“问答、天气、知识库、营销、Agent 编排”五个模块，不要一开始做无人机、农机自动驾驶、大规模传感器接入等复杂功能。
该怎么做
需求边界很重要，它决定你能不能快速做出来。第一版必须只做容易落地、容易展示、容易验证价值的功能。像 IoT、无人机、自动驾驶这些虽然高级，但开发成本高、调试复杂，不适合第一版。

---
3. 总体需求说明
3.1 系统目标
系统要实现一个统一农业 AI 入口，让用户通过一个网页就能完成咨询、查询、检索、生成和辅助决策。
该怎么做
这意味着你的产品要有“一个入口，多个能力”。页面不能做成很多分散的小工具，而要像一个统一的农业智能助手。用户在一个聊天框里提问，系统自动判断是否要调用天气、知识库、营销或其他工具。

---
3.2 核心能力
系统核心能力包括：理解问题、检索知识、调用工具、分析环境和生成结果。
该怎么做
你在设计系统时要把这些能力拆成模块：
- 理解问题：由 LLM 和意图识别完成；
- 检索知识：由 RAG 完成；
- 调用工具：由 MCP 或 Tool Calling 完成；
- 分析环境：由天气模块完成；
- 生成结果：由大模型输出最终内容。
这样每个模块都职责清楚，后期维护会简单很多。

---
4. 功能需求分析
4.1 用户登录与会话管理
系统支持用户登录、历史会话保存、查看和清空。
该怎么做
第一版可以简化登录功能，不一定要复杂账号体系。可以先支持本地演示账号，或者用简单的邮箱密码登录。会话管理要保存用户历史提问和回答，方便复盘和继续追问。
建议至少保留以下字段：用户 ID、会话 ID、问题内容、回答内容、时间戳、Agent 类型。

---
4.2 农业智能问答
用户输入农业问题后，系统给出专业回答。
该怎么做
这个模块是整个项目的核心，应该这样设计：
1. 先判断问题属于哪个类别；
2. 如果需要天气，就先调用天气工具；
3. 如果需要专业资料，就去知识库检索；
4. 如果是营销问题，就切到营销 Agent；
5. 最后由总控 Agent 汇总生成回答。
回答时不要只给结论，还要解释原因，并给出可执行建议。例如：
- 是否适合当前气候条件；
- 为什么这样判断；
- 下一步该怎么做；
- 如果不适合，替代方案是什么。

---
4.3 实时天气模块
显示用户所在地的当前天气和短期预报，并给出农业判断。
该怎么做
你需要一个天气 API，最基本的是根据地区获取：
- 当前温度；
- 湿度；
- 风速；
- 降雨概率；
- 未来 3 到 7 天预报。
然后再做一层农业规则判断，比如：
- 降雨概率高时，不建议喷药；
- 风速过大时，不建议喷洒作业；
- 连续高温时，需要增加灌溉关注；
- 土壤湿度低时，可以提醒补水。
天气模块不要只当展示组件，它必须参与农业决策。

---
4.4 知识库检索增强（RAG）
通过上传文档，建立农业知识库，回答问题时先检索再生成。
该怎么做
知识库建设要分四步：
1. 收集农业资料；
2. 将文档切分成小块；
3. 向量化并存入向量数据库；
4. 问答时先检索相关片段，再交给大模型生成答案。
这样做的原因是：农业问题专业性强，大模型单独回答容易出错。RAG 能把回答限制在你已有资料的范围内，提升准确性和可信度。

---
4.5 多智能体协同
系统根据任务类型，将不同工作交给不同 Agent。
该怎么做
建议先定义几个清晰的 Agent：
- 农业问答 Agent：处理普通农业咨询；
- 天气 Agent：处理天气和环境判断；
- 知识库 Agent：负责检索和引用；
- 营销 Agent：负责广告和内容生成；
- 工具 Agent：负责外部工具调用；
- 调度 Agent：负责分配任务和汇总结果。
协同方式上，先做最简单的路由：用户问题进入后，先判断属于哪类任务，然后调用对应 Agent。后续再扩展成复杂工作流。

---
4.6 MCP 工具接入
让系统通过标准化方式接入外部工具。
该怎么做
你可以把天气、搜索、文件解析、图像识别等能力都封装成工具。MCP 的价值在于把这些工具统一成可调用接口，未来可以随时增加新工具，而不用重写主系统。
第一版不需要把 MCP 做得很复杂，先实现“能接、能调、能返回结果”就可以。

---
4.7 AI 广告生成 Agent
为农产品生成宣传内容，帮助销售。
该怎么做
这个模块最适合做成模板化输入。比如用户输入：
- 产品名称；
- 卖点；
- 目标平台；
- 风格；
- 目标人群；
- 活动信息。
系统生成：
- 标题；
- 文案；
- 短视频脚本；
- 海报文案；
- 直播口播稿。
这样既能体现 AI 能力，也能直接体现商业价值。

---
5. 非功能需求
5.1 性能需求
页面响应要尽量快，普通问答最好在几秒内完成。
该怎么做
要通过以下方式提升性能：
- 前端采用懒加载和流式输出；
- 后端对天气结果做缓存；
- 知识库检索用向量索引；
- 大模型调用尽量使用较快的模型；
- 长文本生成采用分段流式返回。
5.2 可用性需求
系统界面要简单、易懂、易操作。
该怎么做
农业用户不一定熟悉复杂交互，所以页面最好采用“三栏式”：左侧 Agent，中间聊天，右侧天气。这样一眼就能看懂系统在做什么。
5.3 可扩展性需求
后续可以继续增加新 Agent、新工具和新知识库。
该怎么做
在代码层面要把 Agent、Tool、RAG、UI 分层。不要把所有逻辑写在一个文件里，否则后面加功能会很难维护。
5.4 安全性需求
保证 API Key、用户数据和上传文件安全。
该怎么做
所有密钥都放在后端环境变量里，不要写到前端。上传文件要限制大小和类型，避免恶意文件。接口要做权限控制，避免公开滥用。

---
6. 总体架构设计
6.1 分层结构
系统分为展示层、接口层、编排层、能力层和数据层。
该怎么做
这种分层的好处是清晰：
- 展示层负责界面；
- 接口层负责收发请求；
- 编排层负责调用哪个 Agent；
- 能力层负责天气、RAG、营销和工具；
- 数据层负责存储。
如果一开始就按这个结构搭建，后面很容易扩展。

---
6.2 推荐技术选型
- 前端：Next.js + TailwindCSS + shadcn/ui；
- 后端：FastAPI；
- 多 Agent：LangGraph；
- 工具调用：LangChain / MCP；
- 向量数据库：Milvus 或 FAISS；
- 数据库：PostgreSQL；
- 缓存：Redis。
该怎么做
选型要遵循“成熟、资料多、容易快速实现”的原则。不要为了追求新技术而选太复杂的方案。你当前最需要的是快速落地并能演示。

---
7. 技术路线
7.1 第一阶段：快速 MVP
目标是先做出能演示的版本。
该怎么做
先做四件事：
1. 聊天界面；
2. 大模型接入；
3. 天气显示；
4. 基础知识库问答。
这一阶段的重点不是功能多，而是流程跑通。用户能输入问题，系统能返回合理答案，页面能显示天气，这就已经具备基本价值。
7.2 第二阶段：知识增强与工具化
让系统更准确、更专业。
该怎么做
加入文档上传、文本解析、向量检索、引用展示和工具封装。这样系统回答会更稳定，也更像一个真正的农业知识平台。
7.3 第三阶段：多 Agent 协同
让系统从“单模型问答”升级为“任务调度平台”。
该怎么做
把任务拆分成多个子任务，比如天气判断、知识检索、营销文案分别由不同 Agent 处理，再由调度器统一输出。这样你就真正具备了“多智能体”的特征。
7.4 第四阶段：营销与多模态
提升平台展示效果和商业价值。
该怎么做
增加图片识别、海报生成、短视频脚本生成等能力。即使短视频真正生成暂时不做，也可以先做提示词和脚本，作为后续接口预留。

---
8. 模块设计
8.1 前端模块
页面建议包括：顶部导航、左侧 Agent 列表、中间聊天区、右侧天气卡片、文件上传区和历史记录区。
该怎么做
前端不要做成单一聊天框。最好把农业场景相关信息展示出来，例如天气卡片、推荐建议、知识引用、Agent 状态，这样更像一个农业工作台。
8.2 后端模块
后端负责接受请求、调用模型、执行 Agent 编排、管理天气和知识库。
该怎么做
后端 API 至少要分为以下几类：聊天接口、天气接口、知识库接口、营销接口、Agent 路由接口。每个接口只干一件事，便于维护。
8.3 知识库模块
负责文档导入、切分、向量化和检索。
该怎么做
最关键的是文档质量。你应该优先整理高质量农业资料，再做切分策略。切分太大容易检索不准，切分太小又容易缺上下文，因此要找到平衡。
8.4 天气模块
负责天气获取和农业判断。
该怎么做
天气模块要同时输出“天气数据”和“农业建议”。不要只显示数值，还要把数值翻译成用户能直接执行的建议。
8.5 营销生成模块
负责农产品营销内容生成。
该怎么做
要把输出标准化成几种常见格式，比如“标题 + 正文 + 口播稿 + 分镜”，这样用户拿到内容就能直接使用。

---
9. 数据设计
9.1 用户数据
保存用户身份和会话信息。
该怎么做
最少要有用户表和会话表。用户表保存基础身份，会话表保存每次问答，方便历史记录和上下文追踪。
9.2 知识文档数据
保存上传的农业资料和向量索引。
该怎么做
文档解析后保存原文、切分块、标签和向量 ID。这样后续既能检索，也能追溯来源。
9.3 天气数据
保存实时天气和最近一次查询结果。
该怎么做
天气数据可以短期缓存，避免频繁请求外部接口，同时提高响应速度。
9.4 营销任务数据
保存生成内容和输入参数。
该怎么做
这样做有两个好处：一是便于用户再次编辑，二是方便后续统计常见需求和模板优化。

---
10. 接口设计
10.1 聊天接口
接收用户问题并返回答案。
该怎么做
接口应支持会话 ID、用户输入、地区信息和可选文件引用。返回值最好包含：最终答案、引用来源、使用的 Agent、天气信息摘要。
10.2 天气接口
根据地点获取天气。
该怎么做
前端调用后端天气接口，后端再请求天气服务。这样能隐藏 API Key，也便于做缓存和错误处理。
10.3 知识库接口
支持上传、检索和管理。
该怎么做
上传接口负责文件入库，检索接口负责语义搜索，管理接口负责查看文档状态。三者分开更清晰。
10.4 营销生成接口
负责生成农产品内容。
该怎么做
接口需要支持不同平台和风格，这样生成结果更贴近真实使用场景。

---
11. 关键业务流程
11.1 农业问答流程
用户提问后，系统判断是否需要天气、知识库或营销 Agent，再汇总输出。
该怎么做
这个流程最适合做成流程图。实现时先写简单规则版本，再升级为意图识别版本。这样开发节奏更稳。
11.2 文档知识库流程
上传文档、抽取文本、切分、向量化、存储、检索、回答。
该怎么做
这条链路一定要完整。你可以先用少量测试文档验证流程是否跑通，再逐步增加文档数量。
11.3 营销生成流程
输入产品信息后生成多种宣传内容。
该怎么做
最好将同一份输入生成多个结果模板，方便用户选择，而不是只输出一段长文本。

---
12. 开发实施顺序
12.1 第一步：前端框架
先做页面布局和聊天框。
该怎么做
用 Next.js 先搭好首页、聊天区、天气卡片和 Agent 列表，哪怕先是静态页面，也能快速看到产品雏形。
12.2 第二步：后端接口
先跑通问答接口和天气接口。
该怎么做
用 FastAPI 先做基础接口，保证前后端能通信，再逐步接入模型和工具。
12.3 第三步：知识库
接入文档上传和 RAG。
该怎么做
从一小批农业文档开始，验证检索效果，再扩展到更多文档。
12.4 第四步：多 Agent
再加入调度和协同。
该怎么做
先做简单路由，比如关键词判断；后面再做基于 LLM 的意图路由和工作流编排。
12.5 第五步：营销 Agent
增加农业广告生成。
该怎么做
把营销模板固定下来，用户输入内容后，生成标题、文案和脚本，作为项目亮点展示。

---
13. 风险与应对
13.1 大模型幻觉
该怎么做
用知识库约束回答，必要时显示引用来源，减少胡乱生成。
13.2 多 Agent 复杂度高
该怎么做
先单 Agent 再多 Agent，不要一开始就追求复杂工作流。
13.3 工具调用失败
该怎么做
加重试、缓存和降级机制，保证系统可用。
13.4 知识库质量不高
该怎么做
优先整理高质量资料，并定期更新和清洗。

---
14. 测试与验收
14.1 测试项目
- 聊天功能；
- 天气功能；
- 知识库上传；
- 知识库检索；
- 营销内容生成；
- Agent 路由；
- 异常处理。
该怎么做
每个模块都要先单独测试，再做联调。特别是天气、知识库和模型调用，最容易出现接口错误和超时。
14.2 验收标准
- 能回答农业问题；
- 能显示天气；
- 能上传文档并检索；
- 能生成营销内容；
- 能体现多 Agent 协同；
- 页面可正常演示。

15. 项目总结
AgroAgentOS 的核心是把农业知识、天气信息、知识库检索、多智能体编排和营销生成整合到一个平台中。它既有技术展示价值，也有农业场景价值。
该怎么做
当前最合适的做法是先做一个简洁但完整的 MVP：
1. 聊天界面；
2. 实时天气；
3. 农业问答；
4. 知识库；
5. 营销 Agent。
等这几个功能稳定后，再逐步加入 MCP、多 Agent 工作流和多模态能力。这样你会得到一个既能快速落地，又方便后续扩展的农业 AI 平台。
