# AgroAgentOS 强制开发规范设计

## 1. 背景与目标

AgroAgentOS 同时包含 FastAPI 后端、React 前端、微信小程序、LangGraph 多智能体、Skill、MCP 服务、数据库迁移与基础设施配置。仓库已有架构和专项开发文档，但缺少一套由人类开发者与 AI 开发助手共同遵守的统一开发规范。

本设计要建立文档级强制门禁，使后续代码修改具备一致的分层、测试、安全和交付标准。AI 未满足适用门禁时，不得声称任务已经完成、修复或可以交付。

本次工作只设计规范体系，不引入 CI、pre-commit、新的格式化工具或其他自动化设施。稳定规则后续可逐步固化为自动化门禁。

## 2. 采用方案

采用“双层规范”结构：

1. 根目录 `AGENTS.md` 是 AI 强制执行入口，包含不可跳过的核心协议、禁止事项、阶段门禁、验证要求和完整规范链接。
2. `docs/DEVELOPMENT_STANDARDS.md` 是唯一完整规则源，供人类开发者和 AI 开发助手共同遵守。

`AGENTS.md` 不复制完整细则，只保留足以确保 AI 主动读取和执行完整规范的摘要。规则只在完整规范中详细维护，避免两份文档产生冲突或漂移。

## 3. 规范语言与优先级

规范使用以下约束词：

- **必须**：交付门禁，不满足时不得交付。
- **禁止**：任何任务中都不能默认执行的行为。
- **应当**：默认执行；偏离时必须说明具体理由。
- **可以**：在符合任务范围和现有架构的前提下选择执行。

规则优先级为：

1. 用户在当前任务中的明确要求。
2. 根目录 `AGENTS.md`。
3. `docs/DEVELOPMENT_STANDARDS.md`。
4. 目标模块已经形成的局部惯例。

用户指令不能被解释为默认授权泄露凭证、破坏用户未提交改动或执行任务范围外的破坏性操作。遇到冲突时，AI 必须指出冲突并请求明确指示。

## 4. AI 强制工作流

### 4.1 开始编码前

AI 必须：

1. 阅读根目录 `AGENTS.md` 和完整开发规范。
2. 检查工作区状态，识别用户已有的未提交改动并保护这些改动。
3. 阅读目标模块及其相邻实现、测试、schema、配置和文档。
4. 明确需求边界、受影响模块、兼容性风险和最小验证集合。
5. 对多步骤或高风险任务先形成可检查的实施计划。

### 4.2 编码过程中

AI 必须保持最小、聚焦和可回退的改动，遵守现有分层与公开接口。禁止顺手重构无关代码、覆盖用户改动、隐藏错误、绕过类型系统或以删除测试的方式获得通过结果。

新增依赖、改变公开 API、修改数据库结构、改变认证授权语义或引入破坏性行为前，必须评估影响；超出用户已授权范围时必须先获得明确批准。

### 4.3 完成交付前

AI 必须按照改动类型执行对应测试、构建、迁移或静态检查。无法执行某项验证时，必须说明原因、影响、已采用的替代验证和剩余风险。

只有同时满足以下条件，才能使用“完成”“已修复”“可交付”等表述：

- 用户需求已经实现。
- 适用的测试、构建和迁移检查已通过。
- 未引入敏感信息和无关改动。
- 接口、配置、数据库和文档保持同步。
- 最终交付报告完整、准确，没有隐瞒失败或未验证事项。

## 5. 完整规范的章节设计

`docs/DEVELOPMENT_STANDARDS.md` 将包含以下章节。

### 5.1 通用工程原则

定义最小改动、单一职责、兼容性、依赖管理、命名、注释、日志、可观测性、敏感信息保护和遗留代码处理原则。新代码必须符合规范；修改遗留代码时，应在任务范围内消除直接相关的不规范实现，不扩大为无关重构。

### 5.2 Python 与 FastAPI

核心边界如下：

- `api/v1/` 只负责 HTTP 协议、参数解析、依赖注入、鉴权和响应组装。
- 业务逻辑进入 `services/`，路由不得直接访问数据库。
- 基础设施适配和外部系统访问进入 `core/` 或明确的工具适配层。
- 请求和响应使用 `schemas/` 中的 Pydantic 模型，统一响应遵循 `ApiResponse[T]`。
- 可预期业务错误进入 `AppException` 体系，由全局处理器转换为 API 响应。
- 异步请求链路禁止直接执行阻塞 I/O；确有需要时使用异步客户端或显式线程卸载。
- 日志不得记录密码、Token、密钥或完整敏感请求体。

### 5.3 React 与 TypeScript

核心边界如下：

- 页面负责组合和路由级交互，可复用表现与行为进入组件或 hook。
- HTTP 与 SSE 访问集中在 `api/`，不得在页面中重复实现认证和错误处理。
- 跨页面客户端状态使用 Zustand，服务端状态使用 TanStack React Query。
- 类型定义集中在已有 `types/` 结构中；禁止新增无充分理由的 `any`、双重断言或无约束对象。
- 组件必须覆盖加载、空数据、错误和成功状态，并保持基本可访问性。
- 前端代码交付前必须通过 `npm run lint` 和 `npm run build`，除非改动类型明确不适用。

### 5.4 微信小程序

小程序网络、认证和本地存储必须复用现有 `services/` 与 `utils/`。页面必须正确处理生命周期、并发请求、加载态、空态、错误态和登录失效。禁止硬编码后端地址、访问令牌或环境密钥；公共行为不得散落复制到多个页面。

### 5.5 Agent、Skill 与工具

必须保持 `SkillRouter → Planner → Executor → Replanner` 的职责边界：

- 路由器负责选择 Skill，不承载业务工具执行。
- Planner 基于 playbook 生成计划，不直接绕过 Executor 调用工具。
- Executor 统一通过既有运行时执行工具。
- Replanner 负责评估、重试、换路或收敛，必须尊重失败记忆和最大步数。
- 新增 Skill 必须满足 frontmatter、命名、触发词、工具白名单、风险等级和 `inline`/`fork` 模式约定。
- 工具必须声明准确的元数据与风险属性；高风险写操作不得被默认执行。
- LLM 输出必须作为不可信输入进行结构化解析和失败处理，不得假定格式永远正确。

### 5.6 数据库与迁移

任何 ORM 或数据库结构变更都必须附带 Alembic 迁移，并验证升级路径。实现必须考虑 SQLite 开发模式和 MySQL 生产模式的兼容性。结构化文本字段沿用 `_json` 命名与属性解析约定。禁止只修改模型而不提供迁移，或直接改写已有生产迁移来掩盖新变更。

### 5.7 配置、依赖与安全

新增环境变量必须进入 `Settings` 和 `.env.example`，并提供安全默认值或明确的必填校验。真实凭证、Token、Cookie、私钥和本地 `.env` 禁止提交。新增依赖必须说明用途，更新正确的依赖清单，并避免与现有栈重复。

认证、授权、文件上传、外部 URL、命令执行和高风险工具属于安全敏感区域，必须包含输入校验、权限检查、边界限制和失败处理。

### 5.8 API 与兼容性

公开接口变更必须同步路由、schema、服务、调用端、测试与文档。禁止静默改变字段含义、响应结构、鉴权要求或错误码。确需破坏性变更时，必须显式说明影响和迁移方式，并获得用户批准。

### 5.9 测试与验证矩阵

规范使用“改动类型 → 必跑验证”的矩阵：

| 改动类型 | 最低验证门禁 |
| --- | --- |
| Python 单模块业务逻辑 | 相关 `pytest` 测试 |
| 后端跨模块、认证、Agent 核心链路 | 相关测试并运行全量 `pytest` |
| React/TypeScript | `npm run lint`、`npm run build` |
| 微信小程序 | 语法/配置检查及受影响流程的人工或工具验证，并记录验证范围 |
| ORM/数据库结构 | 相关测试、Alembic 升级检查、SQLite/MySQL 兼容性审查 |
| Skill/工具 | 注册加载、路由/白名单、成功与失败路径验证 |
| 配置/启动脚本 | 配置解析、目标命令或等价 smoke test |
| 仅文档 | 链接、命令、路径和内容一致性检查 |

测试失败时只允许修复根因、以证据确认失败与本次改动无关并报告，或将其作为阻塞项交付给用户。禁止删除测试、弱化断言、屏蔽错误或隐瞒失败。

### 5.10 Git、审查与交付

改动应保持单一目的，提交信息采用仓库已使用的约定式语义，例如 `feat:`、`fix:`、`refactor:`、`test:`、`docs:`。AI 不得擅自提交、推送或创建 PR，除非用户或明确工作流要求；无论是否提交，都必须保护用户已有改动。

最终交付报告至少列出：

- 完成的行为变化。
- 关键设计与兼容性说明。
- 修改的文件。
- 实际执行的验证及结果。
- 未执行的验证、原因和替代检查。
- 已知限制与剩余风险。

## 6. 禁止事项

规范将明确禁止以下行为：

- 路由直接读写数据库或包含大段业务逻辑。
- 提交真实密钥、Token、Cookie、密码、私钥或本地环境文件。
- 捕获异常后静默忽略，或向客户端泄露内部堆栈和敏感信息。
- 用 `any`、无约束字典、双重断言或关闭检查来逃避类型问题。
- 修改数据库结构但不提供迁移。
- 硬编码服务地址、密钥或环境专属路径。
- 删除、重置、覆盖或混入用户未提交的无关改动。
- 通过删除测试、降低断言、跳过检查或隐瞒失败来宣称通过。
- 在未验证的情况下声称任务完成。
- 为让某次改动通过而临时放宽开发规范。

## 7. 例外处理

规范门禁不能由 AI 自行豁免。确实无法满足时，AI 必须说明：

1. 无法满足的具体规则。
2. 客观原因。
3. 对正确性、安全性和兼容性的影响。
4. 已执行的替代验证或缓解措施。
5. 剩余风险。

需要偏离强制规则的代码交付，必须获得用户明确批准。仅因时间不足、工具运行较慢、历史代码不规范或修复困难，不构成自动豁免理由。

## 8. 文档同步与维护

架构、命令、环境变量、API、数据库、Agent/Skill 或工具约定变化时，相关文档必须与代码同次更新。

修改开发规范本身时，必须说明修改原因、影响范围和迁移要求。不得为单次任务临时降低门禁。`docs/DEVELOPMENT_STANDARDS.md` 是详细规则的唯一来源；`AGENTS.md` 仅维护执行入口和摘要。

## 9. 实施范围

设计获批后的实施只包含：

1. 更新根目录 `AGENTS.md`，加入 AI 强制开发协议和完整规范链接。
2. 新增 `docs/DEVELOPMENT_STANDARDS.md`，写入完整规则、检查表和验证矩阵。
3. 检查两份文档的一致性、链接、命令和仓库路径。

本轮不修改业务代码，不处理当前工作区中的既有未提交改动，不新增自动化工具，也不建立 CI。

## 10. 验收标准

- 人类开发者能从完整规范明确判断允许、禁止和必须执行的行为。
- AI 从根目录 `AGENTS.md` 能得知必须读取完整规范，并能按任务阶段执行门禁。
- 后端、前端、小程序、Agent/Skill、数据库、配置、安全和 Git 均有明确约束。
- 每类常见改动都能映射到最低验证命令或验证方式。
- 无模糊占位符、互相冲突的重复规则或无法执行的仓库路径。
- 规范明确规定例外审批和未验证事项的报告方式。
